2. Backend (FastAPI #1) — feature-based structure under backend/app/
   Structure:
     app/core/        shared: config, db session, security (bcrypt+JWT),
                       exceptions (one AppError hierarchy -> consistent JSON
                       error shape), dependencies (get_current_user,
                       require_role RBAC), pagination, enums (OrgRole,
                       ActionType ported from legacy audit_logger.py),
                       rate_limit (Redis-backed, fails open), middleware
                       (request-id + slow-request logging)
     app/models/       Base + mixins (UUIDPKMixin, TimestampMixin,
                       TenantMixin) shared by every feature's tables
     app/features/auth/           User, RefreshToken models; signup/login/
                                   refresh/logout/me; JWT access+refresh with
                                   server-side revocation and rotation
     app/features/organizations/  Organization, OrgMembership, OrgInvitation
                                   models; create-org, list/invite/accept/
                                   role-change/remove-member, RBAC-enforced
                                   (owner/admin/member/viewer), last-owner
                                   protections, privilege-escalation guard
                                   (only an owner can grant/revoke owner role)
     app/features/audit/          AuditEvent model (append-only, ported from
                                   legacy audit_logger.py schema incl. secret
                                   redaction rules), record_event() helper
                                   used by auth + organizations, paginated
                                   query endpoint (admin+)
     app/features/dashboard/      stub summary endpoint (zeros) — Phase 2
                                   will replace with real aggregation once
                                   tasks/approvals tables exist
   Design notes:
     - Every tenant-scoped table uses TenantMixin (org_id FK, indexed) so
       tenant isolation can't be forgotten per-table.
     - require_role() dependency resolves :org_id from the path, checks
       membership + role; non-members get 404 (not 403) so org existence/
       membership isn't leaked.
     - Refactored org-creation logic (slug generation, owner membership,
       audit event) into organizations/service.py::create_organization_for_user
       so both /auth/signup (first org) and POST /organizations (additional
       org for an existing user) share one implementation — no duplication.
     - Token issuance (access+refresh, DB-persisted hashed refresh token)
       lives in features/auth/tokens.py specifically to avoid a circular
       import between auth.service and organizations.service (organizations
       needs to log a user in on invite-accept; auth.service needs to create
       an org on signup).
     - Found and fixed a real circular-import bug: app/models/__init__.py was
       eagerly importing all feature models (for Alembic's benefit), but
       Python always initializes a package's __init__ before its submodules,
       and feature models import app.models.base (a submodule of that same
       package) — so importing any feature model re-triggered the
       still-running __init__, which tried to import that same
       not-yet-finished feature module. Fixed by making app/models/__init__.py
       export only Base, and moving the "import every feature's models"
       step into alembic/env.py where it belongs.
   Alembic: alembic.ini, env.py (async, reads DATABASE_URL from app settings)
   are in place. NOT YET DONE: no migration has been generated yet (planned
   next step — will run `alembic revision --autogenerate` against the live
   Postgres container).
   No automated pytest suite written yet for this feature set — verification
   so far has been live (see "Verified working" below).
