# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A **Personal AI Employee (Digital FTE)**: a local-first automation system where Python "watcher" scripts monitor inputs (filesystem, Gmail, WhatsApp, LinkedIn), drop actionable Markdown files into an Obsidian vault, and an **orchestrator** repeatedly invokes the **Qwen Code CLI** (`qwen`) to read/act on those files. Sensitive actions go through a folder-based human-in-the-loop (HITL) approval flow before the orchestrator executes them via the Gmail API.

The project is built in tiers (Bronze → Silver → Gold → Platinum). Currently **Silver Tier is complete** (multiple watchers, HITL approval execution, one MCP server, Task Scheduler integration). Check `README.md` and `AI_Employee_Vault/README.md` for the current tier status before assuming a Gold/Platinum feature (Odoo, social posting, Ralph Wiggum loop, CEO briefings) is finished — some exist as early scaffolding (`ceo_briefing_generator.py`, `ralph_wiggum_hook.py`, `audit_logger.py`) but aren't necessarily wired into the main loop yet.

There is no separate "app" to build/compile — the deliverable is the vault + the Python scripts + the Qwen Code skills. Everything is driven by `qwen` shelling out per task, so **Qwen Code CLI must be installed and in PATH** (`npm install -g @qwen-code/qwen-code`) for any of this to actually run end-to-end.

## Commands

All Python code lives under `AI_Employee_Vault/src/`. Run commands from that directory unless noted.

```bash
cd AI_Employee_Vault/src

# Install dependencies
pip install -r requirements.txt
playwright install chromium   # required for the WhatsApp/LinkedIn watchers

# Verify the Qwen Code CLI is present (everything depends on this)
qwen --version

# Full diagnostic sweep (deps, folders, Gmail auth, watcher scripts, live file-drop test)
python test_system.py

# Component-by-component test harness (imports, CLI --help, dashboard/audit/briefing scripts,
# live file-drop, a 10s watcher smoke-start) — pass the vault path
python test_components.py ..

# Gmail OAuth2 one-time (re-)authentication
python authenticate_gmail.py ..\.cache\gmail_credentials.json

# Run a single watcher (vault_path is always the first positional arg; each has its own
# check_interval default — see its --help / source for options)
python filesystem_watcher.py ..
python gmail_watcher.py .. ..\.cache\gmail_credentials.json
python whatsapp_watcher.py ..
python linkedin_watcher.py ..

# Run the orchestrator (polls Needs_Action/ and Approved/, triggers `qwen`, executes approvals)
python orchestrator.py .. [check_interval_seconds]

# One-off utility invocations (each also has --help)
python dashboard_updater.py .. --once
python audit_logger.py .. --action test --target testing --actor test_script
python ceo_briefing_generator.py ..
python ralph_wiggum_hook.py --help
```

Windows helpers (from `AI_Employee_Vault/src/scheduler/`):

```batch
start_all_watchers.bat ..      REM launches every watcher + orchestrator in separate windows
stop_all_watchers.bat
```


There is no linter, formatter, or pytest suite configured (`test_system.py` / `test_components.py` are diagnostic/manual-verification scripts, not automated unit tests — they print pass/fail and often need a running watcher to actually pass). When changing watcher/orchestrator logic, the practical verification loop is: drop a file in `Inbox/`, tail the orchestrator's terminal output, and check `Logs/<YYYY-MM-DD>.log`.

## Architecture

### The vault is the state machine

`AI_Employee_Vault/` is an Obsidian vault whose top-level folders **are** the pipeline stages. Every watcher and the orchestrator moves files between these folders instead of using a database or queue:

```
Inbox/ → Needs_Action/ → (Plans/ for complex tasks) → Pending_Approval/ → Approved/|Rejected/ → Done/
```

- **Inbox/** — raw drop folder; only the Filesystem Watcher reads this.
- **Needs_Action/** — every watcher's real output target: one `.md` action file per detected item (email, file, chat message...). The orchestrator's main loop only ever looks here for the *next* item (oldest `mtime` first, one at a time).
- **Plans/** — `PLAN_*.md` files auto-generated by `Orchestrator.analyze_task_complexity()` when a task looks like it needs 2+ steps (checkboxes, multiple `?`, keywords like "research"/"analyze"/"compare"). Purely advisory context for Qwen; the orchestrator doesn't gate on plan completion.
- **Pending_Approval/** → **Approved/** / **Rejected/** — the HITL gate. A human (or Qwen, per its prompt) writes an `APPROVAL_*.md` file with YAML frontmatter (`type`, `action`, `to`, `subject`, `status`) and a `## Draft Content` body; moving that file into `Approved/` is the only trigger the orchestrator recognizes to actually execute anything external (send email, etc.) — see `Orchestrator.process_approved_items()` in `orchestrator.py`. Moving to `Rejected/` just archives it.
- **Done/** — terminal state for anything the orchestrator or Qwen has finished with, plus execution logs get cross-referenced here.
- **Logs/** — daily `.log` (via Python `logging`) and daily `.md` (human-readable execution journal) files, plus `Logs/Failed_Executions/` for approvals whose execution threw.

Because file movement *is* the protocol, any new automation must respect this contract: create one `.md` file per unit of work in `Needs_Action/`, never write directly into `Approved/`, and never assume another process's file is safe to touch mid-move (watchers checkpoint processed-IDs to `*.cache/*_processed.txt` precisely to survive races/restarts).

### Watcher pattern (`base_watcher.py`)

Every watcher (`filesystem_watcher.py`, `gmail_watcher.py`, `whatsapp_watcher.py`, `linkedin_watcher.py`) subclasses `BaseWatcher` (ABC) and implements exactly two methods:

- `check_for_updates() -> list` — poll the source, return new items.
- `create_action_file(item) -> Path` — write one Markdown file into `Needs_Action/` with YAML frontmatter describing the item, and mark it processed.

`BaseWatcher.run()` owns the poll loop, logging setup (`Logs/<date>.log`), and folder creation — subclasses never reimplement the loop. Dedup across restarts uses `load_processed_ids()` / `save_processed_ids()` (flat text files under `.cache/`), keyed per-watcher-name. When adding a new watcher, follow this exact shape rather than inventing a new mechanism.

### Orchestrator (`orchestrator.py`)

Single-threaded polling loop (`Orchestrator.run()`, default 30s interval) that each cycle:

1. Updates `Dashboard.md` counts (string `.replace()` on known placeholder rows — the dashboard template's exact placeholder text matters, this is not a templating engine).
2. Calls `process_approved_items()` — parses each file in `Approved/` (`parse_approval_file()` reads YAML frontmatter + the `## Draft Content` section), dispatches by `type` (`email` → `execute_email_action()` via Gmail API, `whatsapp` → logged for manual send, anything else → `execute_generic_action()`), writes an execution log, and moves the file to `Done/` or `Logs/Failed_Executions/`.
3. Picks the single oldest file in `Needs_Action/` and calls `process_with_qwen()`: runs complexity analysis, optionally writes a `Plans/PLAN_*.md`, then shells out to `qwen -p "<prompt>" -y` (via `subprocess.run`, `shell=True` on Windows) with a hardcoded prompt instructing Qwen to read the task, read `Company_Handbook.md`, write a `RESPONSE_<file>.md`, move the original to `Done/`, and print the sentinel `<TASK_COMPLETE/>`. Qwen's own stdout streams straight to the orchestrator's terminal (not captured) — that terminal *is* the UI for seeing what the AI did.

Gmail sending (`execute_email_action`) and the Gmail watcher both read/write the **same** `.cache/gmail_token.pickle`, but need different OAuth scopes (`gmail.readonly` for watching vs `gmail.send`+`gmail.compose`+`gmail.readonly` for sending) — a token authorized only for reading will force re-auth the first time an approval tries to send.

### Company_Handbook.md is the policy file

Qwen is instructed (via the orchestrator's prompt) to read `Company_Handbook.md` before acting. This is where approval thresholds, tone/style rules, and escalation keywords live — it's the mechanism for changing AI behavior without touching code.

### Qwen Code skills (`.qwen/skills/`)

Reusable instructions for Qwen Code itself, versioned in `skills-lock.json`:
- `ai-employee-bronze/`, `ai-employee-silver/` — the tiered task-processing skill definitions (what to do with a `Needs_Action/` file, templates for plans/approvals/logs).
- `browsing-with-playwright/` — a Playwright MCP server + a universal HTTP/stdio MCP client (`scripts/mcp-client.py`) for browser automation, used by the WhatsApp/LinkedIn watchers and available to Qwen for general browsing tasks.

### MCP servers (`AI_Employee_Vault/src/mcp_servers/`)

`email_mcp_server.py` exposes Gmail send/draft/search as MCP tools over stdio, for use *from Qwen Code* (as opposed to the orchestrator's direct Gmail API calls for executing approvals). Expect Silver-tier scope here (email) — Gold tier's planned Odoo/social MCP servers don't exist yet.

## Windows-specific notes

This project is developed and run on Windows (paths, batch scripts, PowerShell Task Scheduler registration, `qwen -p "..."` invoked with `shell=True` specifically to resolve `qwen.cmd`). Path separators in docs/scripts are typically backslash; when writing new Python, keep using `pathlib.Path` (already the convention) so it stays portable.

## Secrets

`AI_Employee_Vault/.cache/` holds `gmail_credentials.json`, `gmail_token.pickle`, and per-watcher processed-ID caches. `.gitignore` already excludes `.cache/`, `*.pickle`, and `credentials.json` (see `SECURITY_AND_GITIGNORE.md`) — never override that or otherwise commit real tokens/credentials. Note `AI_Employee_Vault/Inbox/`, `Needs_Action/`, `Pending_Approval/`, `Approved/`, and `Rejected/` are also gitignored wholesale (working data, potentially sensitive), while `Done/`, `Plans/`, `Briefings/` are tracked by default — keep that in mind before writing anything sensitive into the latter three.
